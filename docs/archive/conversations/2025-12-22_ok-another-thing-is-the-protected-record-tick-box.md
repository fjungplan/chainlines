### Planner Response

Running pgAdmin in a Docker container versus natively on Windows is a common choice. Since your current project already uses a Docker-based workflow (Caddy, FastAPI, Postgres, and React all containerized), here is how the two approaches compare:

### 1. Running pgAdmin in Docker (Recommended for your current setup)

**Benefits:**
*   **Infrastructure as Code:** You can add pgAdmin directly to your [docker-compose.yml](cci:7://file:///c:/Users/fjung/Documents/DEV/chainlines/docker-compose.yml:0:0-0:0). This means anyone who clones your repo gets the database AND the management tool with one command (`docker-compose up`).
*   **Internal Networking:** Inside the Docker network, pgAdmin can talk to your database using the service name `postgres` instead of `localhost`. This is often more stable and mimics a production environment.
*   **Zero "Pollution":** No registry keys, no background services running on Windows when you aren't coding, and no dependency conflicts. When you're done, `docker-compose down` cleans everything up.
*   **Version Control:** You can pin pgAdmin to a specific version that you know works with your Postgres 15 image.

**Downsides:**
*   **Networking Logic:** You have to understand that "localhost" inside the pgAdmin container is NOT your Windows machine, which can be confusing at first.
*   **Persistence:** You must map a volume to save your server connections; otherwise, they disappear when the container is deleted.

### 2. Running pgAdmin Natively on Windows

**Benefits:**
*   **Familiarity:** It feels like a standard Windows app. You can pin it to your taskbar and launch it independently of your project.
*   **OS Integration:** Easier interaction with your local file system (e.g., if you want to export a CSV directly to your `Documents` folder).
*   **Performance:** Slightly less overhead since it doesn't go through the Docker Desktop/WSL2 abstraction layer (though for a UI tool, this is negligible).

**Downsides:**
*   **Manual Setup:** You have to manually download, install, and update it on every machine you use.
*   **External Access:** You must ensure your Docker container maps port `5432` to your host (which your current setup does), or pgAdmin won't be able to "see" the database.

| **Isolation** | High (contained) | Low (system-wide) |
| **Networking** | Internal Docker DNS | Host-loopback (`localhost`) |
| **Resource Use** | Part of Docker Engine | Separate Windows Process |

## UI Option Analysis (Form-based vs Diff-based)

### Option A: Form-based (Recreated CRUD)
Create a "Review" version of each specific editor (Team Node, Era, Sponsor, Lineage, etc.).
- **Pros**:
    - **Familiarity**: Moderators see the same form as the editor.
    - **Context**: Full validation logic and surrounding fields are visible (e.g. seeing other eras when editing one).
    - **Non-Technical**: Hides the underlying data structure completely.
- **Cons**:
    - **Maintenance**: Requires maintaining 6+ distinct "Review" components in sync with "Edit" components.
    - **Complexity**: "Read-Only" state for complex forms (like drag-and-drop lineage) is hard to implement side-by-side with an editable version.
    - **Overkill**: Opening a massive form just to approve a typo fix slows down the workflow.

### Option B: Structured Diff (Pseudo-code / Side-by-Side)
A generic, recursive comparison view. Left = Original JSON (formatted), Right = Proposed JSON (editable).
- **Pros**:
    - **Efficiency**: Highlights *only* what changed. High-velocity moderation.
    - **Scalability**: One component handles all 6 record types (and future ones).
    - **Transparency**: Shows exactly what data will be written to the DB.
- **Cons**:
    - **Technical feel**: Requires moderators to understand keys like `legal_name` or `valid_from` (though we can map these to labels).
    - **Context Loss**: A "Diff" might not show that `valid_from` overlaps with another era unless we specifically fetch and display that context.

### Recommendation
**Hybrid Approach**: Use **Option B (Structured Diff)** but with **"Smart Labels"**.
- Use the generic diff engine for speed and maintainability.
- Apply a mapping layer: Display `Founding Year` instead of `founding_year` and `Visma (Sponsor)` instead of `5f3a...`.
- This gives the speed of a diff with the readability of a form.
